元宝浏览器「记得住」对底座的接口需求
游杰 → 琛哥 · 2026.06.02
一句话：「记得住」是底座的头号客户，本文不讨论业务怎么做，只对齐底座要为我提供什么能力、什么时候提供、谁兜什么责任。

1先对齐两个核心概念

记忆（Memory）

用户在浏览器内沉淀下来的长期可复用资产。包括：

  • 显性资产：书签、笔记、收藏、文件、AI 对话记录、用户主动标记
  • 隐性资产：浏览行为（停留时长、跳转路径、复访）、搜索历史、内容偏好

关键属性：跨会话存在、可被检索、可被 AI 调用。

上下文（Context）

用户当前会话/任务内的短期工作集。包括：

  • 当前打开的标签页、当前阅读的内容、当前任务的中间产物
  • 本次对话的历史轮次、当前页面的语境注入

关键属性：短生命周期、高频读写、需要快速注入到 LLM。

两者关系：上下文是入口（用户当下在做什么），记忆是弹药库（过去沉淀的资产）。
「记得住」业务的本质 = 把上下文实时翻译成检索意图，从记忆里召回相关资产，注入给 AI。

2我用你的底座哪几层

L0 · 账号通道（UnionID）
跨端用户身份统一，让 PC/移动/元宝/输入法看到同一个用户。我不重做，全用你的。
L1 · 资产存储底座
5 类资产（书签/图片/文件/摘录/AI 对话）的统一 CRUD、版本管理、冲突解决。我把业务 schema 映射到你的底层 schema。
L2 · 跨端同步通道
PC ↔ 移动 ↔ 元宝矩阵 资产实时/准实时同步。push/pull 策略、冲突合并、断点续传。
L3 · 索引与检索（待对齐归属）
向量索引、全文索引、混合检索。性能/准确率敏感，可能你做底座我做策略，也可能我自建。这是核心待决策点。
L4 · 业务层（我做）
「记得住」三层业务能力：自动打标摘要 / 聚类整理 / 召唤过往。Skill 沉淀、轻量手势交互、RAG 业务编排。

边界规则：底座 schema 你定，业务 schema 我定怎么映射；通用组件你做，业务 Skill 我做；数据安全/同步一致性你兜，检索准确率/业务策略我兜。

3具体接口需求清单

接口用途优先级预期

4待你拍板的 3 件事

决策 1：索引层（L3）谁建？

背景：「记得住」要做 RAG 检索，需要向量索引 + 全文索引。

  • 方案 A：你底座建统一索引服务，我调 API
  • 方案 B：我自建（用算法侧的能力），你只提供原始数据

我的倾向：A。理由：索引是底座能力的天然延伸，未来元宝矩阵其他产品也要用。

决策 2：实时事件订阅要不要做？

背景：AI 自动打标/摘要需要在用户新增资产后秒级触发。

  • 方案 A：底座提供事件订阅（WebSocket/SSE），我订阅后触发算法
  • 方案 B：我轮询，简单但延迟高、浪费 IO

我的倾向：A。理由：MVP 阶段可以接受方案 B 兜底，但长期必走 A。

决策 3：跨产品授权机制何时上？

背景：元宝读浏览器资产、输入法读浏览器资产，必须有用户授权流程。

  • 方案 A：MVP 不上，先做内部 dogfood
  • 方案 B：MVP 就上，但产品/法务/UX 都要拉

我的倾向：A（先验证价值，授权机制 V2 再加）。
