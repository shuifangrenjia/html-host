一、为什么需要记忆系统

US1 冷启动 —— 开箱即知用户是谁

现状痛点：养龙虾，成本高

竞品现有产品的体验
ChatGPT / Claude / Gemini白板，需要用户自我介绍
Kimi / 通义千问 / 豆包 / 元宝同上，纯靠对话积累
OpenClaw / WorkBuddy / Hermes部分支持账号导入记忆，但依赖用户主动填写

QB内体验：浏览器独有护城河，业界席位空缺

浏览器拥有用户完整的数字足迹（书签/历史/下载），这是其他AI产品不具备的天然资产。

这个体验目前业界完全空白，谁先做出来谁就占据"有最强记忆能力的AI助手"这个心智位。

US2 跨端任务记忆——从"本地工具"到"跟随用户的伙伴"

WorkBuddy / Claw 体系的死穴：换设备 = 失忆

  • 所有任务数据存本地，各端独立存储，不互通
  • 用户必须重新描述需求

QB内体验：记忆跟着人走，不跟着设备走

二期实现跨session读取任务，工程链路较为复杂。

US3 隐式偏好学习：用户不用说，系统自己看出来

业界对比

产品偏好学习能力
ChatGPT需要用户主动写偏好声明
大部分AI助手（如千问等）无持久化偏好记忆
少部分AI助手（如WorkBuddy）需要用户明确表示记住xxx，或手动修改记忆内容

背后的机制

需要提需给 Tmemory 制定 Dreaming 的业务逻辑。

阶段用户行为系统动作
第1次"帮我生成报告，转成HTML"任务完成 + 记录 delivery_format=html
第2次"再出一版市场分析的，还是要HTML"delivery_format=html 的记录 +1
第3次"这份也转HTML吧"delivery_format=html 的记录 +1
Dreaming— —读取session记录发现任务产出文件格式较多为html，且判断是用户主动要求 → 触发写入"用户偏好HTML格式交付"
架构选择负责人：@xianyizhang（张贤谊）

二、记忆写入逻辑

2.1 冷启机制 —— 浏览器数据驱动的上下文构建

数据来源与价值

数据源关键字段采集范围提取价值
书签title / date / urlURL去重后全量兴趣标签集、职业方向、活跃平台
历史记录title / date / url近90天 / 10000条内近期关注点趋势
下载记录file_name / file_type / source_url / downloaded_at / file_size近90天强意图信号（下载 = 真正在用的）

输出物：结构化画像（写入用户画像）

维度示例
职业"技术开发者"
兴趣标签集["前端开发", "AI/ML", "React", "论文阅读"]
近期关注点["React 19新特性", "RAG优化"]
活跃平台["GitHub", "知乎", "掘金"]

要点

  • 更新策略：冷启动一次性全量生成 + 每周增量刷新（仅活跃用户）
  • 二期扩展：DataSource接口可插拔，支持接入新产品内容源（如输入法词库）

2.2 会话机制

【用户画像】User Profile —— "这个人是谁？" + "这个人喜欢/讨厌什么？"

固定槽位

槽位 Key说明示例
profession职业/身份产品经理、学生、自由职业者
location所在城市深圳、北京
company公司/学校腾讯、清华
role_context在当前单位中的角色AI资产负责人
language语言偏好中文优先、中英混用
tech_background技术背景前端开发、完全不懂技术
interest_tag兴趣标签集前端开发、AI/ML、React、论文阅读
recent_focus近期关注点React 19新特性、RAG优化
active_web活跃平台GitHub、知乎、掘金
primary_use_case主要使用场景工作提效、学习辅助、生活助手
communication_style沟通风格偏好简洁直接、详细解释、随意聊天
content_style内容风格偏好详细/简洁/口语化/专业
delivery_format交付格式偏好HTML / PDF / Markdown / 长图
avoidance_preference倾向回避别发表情包 / 别说某个词"XX"
explicit_evaluation显式评价点赞 / 踩 / 口头评价

开放扩展区（上限30条）：模型自行判断有价值的非槽位信息

【用户画像】更新机制

显性表达（实时）—— 对话中，直接调用记忆写入工具

触发条件示例
用户显式声明身份"我是做PM的"
显式反馈 / 点赞踩点赞某次输出 / "太长了别这样"
用户明确要求记住"帮我把这个记住"

对话推断（1日）—— 每日 Dreaming

行为推断（7日）—— 用户消费日志更新（增量书签、历史记录等）

【用户画像】冲突处理规则

显式表达 > 对话推断（1日更新） > 行为推断（7日更新）

【关键事件】Task —— "这个人最近在忙什么？"

  • 关键特性：有时效性；跨端可见；来源唯一（仅从session摘要提取）
  • 存储策略：按时间线追加，支持跨端查询
属性说明
title任务标题
summary任务摘要（不含细节，细节归 Session RAG 管）
statusin_progress / completed / abandoned
source来源session摘要ID

【关键事件】更新机制

  • 每5次对话进行一次摘要总结
  • 每日 dreaming 做 session 级 task 摘要

【关键事件】按场景分桶存储

二期考虑按场景分桶存储及召回（如区分浏览器场景和输入法场景），兼容不同用户场景体验。

2.3 Dreaming 演进路线（二期依赖给 Tmemory 提需）

阶段能力复杂度
一期记忆日志 + 每日摘要批处理session级聚合，以天维度抽象用户的task和画像信息
二期异步跨session匹配发现周期性模式（如"每周五问周报"）
二期记忆淘汰降权过期记忆清理

五、记忆系统接输入法

5.1 输入法的冷启动资产对标

浏览器的"书签 / 历史 / 下载" 输入法 可提取的记忆
书签 → 长期兴趣常用词库 / 自定义短语 / 专业术语集兴趣领域、职业关键词
历史记录 → 近期关注输入日志（最近打过的字/词/句）近期话题、项目语境
下载记录 → 强意图剪贴板历史 / 分享到App的记录实际产出的东西
（无）使用场景识别（聊天 vs 文档 vs 搜索 vs 填表）场景化记忆，驱动不同联想
（无）打字习惯（速度 / 错误率 / 中英切换频率）输入法独有的高价值信号
（无）纠错历史（经常改什么错别字）个人化纠错模型的数据源
